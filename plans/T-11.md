# Plan de T-11

## Objetivo

Cumplir REQ-007 con DEC-002 (ajustado por DEC-009), DEC-004 y DEC-005:

- `orchestration/daily.yaml` es el Workflow `compras-diario`. Ejecuta en este orden: el Cloud Run Job
  `compras-mercadopublico`, el job `compras-indicadores`, la compilación de Dataform desde `main` y la invocación de
  Dataform con las etiquetas `silver` y `gold`. Espera a que cada paso termine. Los dos jobs se lanzan con el conector
  `googleapis.run.v2.projects.locations.jobs.run`, que espera la operación, con `connector_params.timeout: 25200` (7 h,
  igual al timeout de tarea de los jobs que fijó T-08). La compilación pasa
  `codeCompilationConfig.vars.raw_dataset`. `vars.policy_tag_rut` lo agrega T-14 (lo dice la descripción de T-11), así
  que E2 queda cubierto en parte hasta T-14. La invocación se consulta hasta que `state` sea `SUCCEEDED`, `FAILED` o
  `CANCELLED`. Si es `FAILED` o `CANCELLED`, el Workflow levanta una excepción. Ningún paso de ingesta está dentro de un
  `try` (E3).
- `infra/modules/orchestration` declara lo siguiente:
  - el repositorio Dataform `compras-publicas-cl`, con remoto GitHub (`https://github.com/<github_repository>.git`, rama
    `main`) y el token en el secreto `dataform-github-token`, que ya existe sin versiones (DEC-004; según DEC-009 es
    fine-grained, limitado al repo, con Contents: read and write y con caducidad, y lo carga el usuario);
  - el Workflow con la cuenta `compras-workflow`;
  - un job de Cloud Scheduler `30 23 * * *` en `America/Santiago` (E1) con su propia cuenta `compras-scheduler`, que
    lanza una ejecución del Workflow;
  - una política de alertas de Cloud Monitoring sobre ejecuciones fallidas del Workflow, con el canal de correo (E4).
- El horario y la zona horaria son variables de Terraform (DEC-002, «Neutrales»).
- `npm run test:orchestration` corre las pruebas estructurales del YAML (pytest + pyyaml) y las del script de
  integración, sin red (DEC-005). `npm run test:infra` comprueba E1 y E4 con `mock_provider`.
- `scripts/it/run-workflow.sh` lanza una ejecución real del Workflow y espera su estado final. Es el
  `verify_integration` y cubre la primera corrida real de DEC-002 y E5.

## Pasos

1. **Workflow `orchestration/daily.yaml`.** Crear el archivo con un solo bloque `main` y estos pasos, en este orden y
   con estos nombres:
   1. `init` (`assign`):
      - `project: ${sys.get_env("GOOGLE_CLOUD_PROJECT_ID")}`
      - `location: ${sys.get_env("GOOGLE_CLOUD_LOCATION")}`
      - `repository: ${"projects/" + project + "/locations/" + location + "/repositories/" + sys.get_env("DATAFORM_REPOSITORY")}`
      - `raw_dataset: ${sys.get_env("RAW_DATASET")}`
      - `dataform_sa: ${sys.get_env("DATAFORM_SERVICE_ACCOUNT")}`

      Las cuatro variables de usuario las fija Terraform (paso 5).
   2. `ingesta_mercadopublico`:
      - `call: googleapis.run.v2.projects.locations.jobs.run`
      - `args.name: ${"projects/" + project + "/locations/" + location + "/jobs/" + sys.get_env("JOB_MERCADOPUBLICO")}`
      - `args.connector_params.timeout: 25200`, sin `skip_polling`
      - `result: ejecucion_mp`
   3. `ingesta_indicadores`: igual que el paso 2, con `JOB_INDICADORES` y `result: ejecucion_indicadores`.
   4. `compilar_dataform`:
      - `call: http.post`
      - `url: ${"https://dataform.googleapis.com/v1/" + repository + "/compilationResults"}`
      - `auth: {type: OAuth2}`
      - `body.gitCommitish: main`
      - `body.codeCompilationConfig`: `defaultDatabase: ${project}`, `defaultLocation: ${location}` y
        `vars: {raw_dataset: ${raw_dataset}}`. `defaultDatabase` es necesario porque `dataform/workflow_settings.yaml`
        trae un proyecto de relleno.
      - `result: compilacion`
   5. `revisar_compilacion` (`switch`): si `"compilationErrors" in compilacion.body`, hace
      `raise: ${compilacion.body.compilationErrors}`.
   6. `invocar_dataform`:
      - `call: http.post`
      - `url: ${"https://dataform.googleapis.com/v1/" + repository + "/workflowInvocations"}`
      - `auth: {type: OAuth2}`
      - `body.compilationResult: ${compilacion.body.name}`
      - `body.invocationConfig`: `includedTags: ["silver", "gold"]`, `transitiveDependenciesIncluded: true`,
        `serviceAccount: ${dataform_sa}`
      - `result: invocacion`
   7. `esperar_dataform`: `call: sys.sleep` con `seconds: 60`.
   8. `consultar_dataform`:
      - `call: http.get`
      - `url: ${"https://dataform.googleapis.com/v1/" + invocacion.body.name}`
      - `auth: {type: OAuth2}`
      - `result: estado`
   9. `evaluar_dataform` (`switch`):
      - `estado.body.state == "SUCCEEDED"` → `next: fin`;
      - `estado.body.state == "FAILED" or estado.body.state == "CANCELLED"` → `raise` con un mapa que nombra la
        invocación y su estado;
      - si no → `next: esperar_dataform`.
   10. `fin`: `return` con los nombres de las dos ejecuciones de los jobs y el de la invocación.

   No hay ningún `try`, `retry` ni `except` en el archivo. Un comentario de cabecera, en inglés como el resto del
   código, cita REQ-007 y DEC-002. Las expresiones `${…}` van entre comillas cuando contienen `:` o empiezan el valor
   de un mapa en línea.

3. **`scripts/it/run-workflow.sh`** (ejecutable, mismo estilo que `scripts/it/run-jobs.sh`).
   - Cabecera:
     - uso: `GOOGLE_CLOUD_PROJECT=… GCP_REGION=… scripts/it/run-workflow.sh [--expect-failure]`;
     - opcionales: `WORKFLOW` (por defecto `compras-diario`), `IT_TIMEOUT` (segundos, por defecto 27000) e
       `IT_POLL` (por defecto 30);
     - códigos de salida: 2 con un argumento inválido o sin `gcloud`/`curl`; 1 si falta una variable o falla un
       chequeo; 0 si todo pasa.
   - Pasos del script:
     1. Guarda `inicio=$(date -u +%Y-%m-%dT%H:%M:%SZ)`.
     2. Lanza la ejecución con
        `gcloud workflows execute "$WORKFLOW" --location="$GCP_REGION" --project="$GOOGLE_CLOUD_PROJECT" --format='value(name)'`.
     3. Consulta en un bucle `gcloud workflows executions describe "$nombre" --format='value(state)'` hasta un estado
        distinto de `ACTIVE`, o hasta `IT_TIMEOUT` (sale con 1 y un mensaje si se acaba el tiempo).
   - Sin argumentos, exige `SUCCEEDED` e imprime `run-workflow: ok execution=<nombre>`.
   - Con `--expect-failure` (E5), exige que se cumplan las tres cosas:
     - el estado es `FAILED`;
     - el error de la ejecución (`--format='value(error.context)'`) nombra `ingesta_mercadopublico`;
     - no hay invocaciones de Dataform creadas después de `inicio`. Esto se consulta con
       `curl -fsS -H "Authorization: Bearer $(gcloud auth print-access-token)"` a
       `https://dataform.googleapis.com/v1/projects/$GOOGLE_CLOUD_PROJECT/locations/$GCP_REGION/repositories/compras-publicas-cl/workflowInvocations`
       y se comparan las `createTime` con `inicio` usando `python3`.

     Después imprime un recordatorio de revisar el correo de la alerta y de volver a habilitar la versión del ticket.
     La cabecera documenta el procedimiento de E5: el usuario deshabilita la versión vigente del ticket con
     `gcloud secrets versions disable <n> --secret=mercadopublico-ticket`, corre el script con `--expect-failure` y
     después la vuelve a habilitar con `enable`. El script no modifica secretos.
   - Nunca imprime el token de acceso.
   - Agregar `orchestration/tests/test_run_workflow.py`, que corre el script con un `gcloud` y un `curl` falsos
     escritos en `tmp_path` y antepuestos al `PATH`, igual que las pruebas de `scripts/ci/tests/test_scripts.py`. Casos:
     - un argumento desconocido sale con 2;
     - sin `GOOGLE_CLOUD_PROJECT` sale con 1 y nombra la variable;
     - `ACTIVE` y después `SUCCEEDED` sale con 0;
     - `FAILED` sin `--expect-failure` sale con 1;
     - con `--expect-failure`, `FAILED` en `ingesta_mercadopublico` y la lista de invocaciones vacía, sale con 0;
     - con `--expect-failure` y una invocación posterior a `inicio`, sale con 1.

## Supuestos

- El conector `googleapis.run.v2.projects.locations.jobs.run` espera por defecto a que termine la operación de larga duración de la ejecución del job, y levanta una excepción si la ejecución falla (guía de conectores de Workflows, T-02 §(a)).
- `connector_params.timeout` se expresa en segundos y admite 25200 (T-02 §(a): hasta un año).
- Workflows expone `GOOGLE_CLOUD_PROJECT_ID` y `GOOGLE_CLOUD_LOCATION` como variables de entorno integradas, y `user_env_vars` no puede usar claves que empiecen con `GOOGLE`.
- La API v1 de Dataform acepta `gitCommitish`, `codeCompilationConfig.defaultDatabase`, `defaultLocation` y `vars` en `compilationResults.create`, y devuelve `compilationErrors` en la respuesta cuando la compilación falla.
- `workflowInvocations.create` acepta `invocationConfig.includedTags`, `transitiveDependenciesIncluded` y `serviceAccount`, y `workflowInvocations.get` devuelve `state` con los valores `RUNNING`, `SUCCEEDED`, `CANCELLED`, `FAILED` o `CANCELING`.
- La métrica `workflows.googleapis.com/finished_execution_count` existe sobre el recurso `workflows.googleapis.com/Workflow`, con la etiqueta de métrica `status` (valor `FAILED` en las ejecuciones fallidas) y la etiqueta de recurso `workflow_id`.
- `google_dataform_repository`, `google_workflows_workflow` (con `user_env_vars` y `deletion_protection`), `google_cloud_scheduler_job`, `google_monitoring_alert_policy`, `google_cloud_run_v2_job_iam_member` y el data source `google_monitoring_notification_channel` existen en `hashicorp/google` 8.8.0. `google_project_service_identity` existe en `google-beta` 8.8.0, admite `dataform.googleapis.com` y exporta `member`.
- `infra/bootstrap` ya está aplicado y su canal `Budget alerts` de tipo `email` es el único con ese nombre en el proyecto.
- El modo act-as estricto de Dataform rige para todos los repositorios: la cuenta que crea la invocación (`compras-workflow`) necesita `iam.serviceAccounts.actAs` (`roles/iam.serviceAccountUser`) sobre la cuenta efectiva, que es la de `invocationConfig.serviceAccount` (`compras-dataform`).
- `roles/iam.serviceAccountAdmin` incluye `iam.serviceAccounts.setIamPolicy`, el permiso con el que CI aplica los grants a nivel de cuenta de servicio.
- El agente de servicio de Dataform necesita `roles/secretmanager.secretAccessor` sobre el secreto del token, y `roles/iam.serviceAccountUser` más `roles/iam.serviceAccountTokenCreator` sobre `compras-dataform`.
- `roles/run.invoker` sobre un job permite `run.jobs.run`, y `roles/run.viewer` en el proyecto permite consultar la operación y la ejecución que espera el conector.
- `roles/storage.admin` o `roles/bigquery.admin` de CI incluyen `resourcemanager.projects.get`, y `roles/monitoring.editor` permite listar canales y crear políticas de alertas.
- Cloud Scheduler puede lanzar una ejecución con `POST` a `workflowexecutions.googleapis.com/v1/<workflow>/executions` con un `oauth_token` de una cuenta que tiene `roles/workflows.invoker`.
- Al deshabilitar la última versión del secreto `mercadopublico-ticket`, el job de Mercado Público no puede leer `latest` y termina distinto de 0.
- El usuario carga la versión del token de GitHub en `dataform-github-token` antes del primer `apply` que crea el repositorio (DEC-004, DEC-009).
- `pyyaml` 6.0.3 y `pytest` 9.1.1 ya están en el entorno local después de `scripts/setup.sh` (grupo `dev` de `pyproject.toml`).

## Riesgos

- Workflows rechaza el YAML con un error de sintaxis o de expresión, y eso solo aparece en el `apply` real porque no hay
  validador local. Lo cubren los pasos 1 y 2: las pruebas estructurales parsean el archivo y comprueban cada campo
  usado. El `verify_integration` (paso 3) lo detecta en la primera ejecución.
- Terraform interpreta los `${…}` de Workflows. El paso 5 usa `file()` y la prueba `t11_workflow` compara
  `source_contents` con el archivo tal cual.
- La compilación usa el proyecto de relleno de `workflow_settings.yaml`. El paso 1.4 pasa `defaultDatabase` y
  `defaultLocation`, y el paso 2 comprueba `defaultDatabase`.
- Una compilación con errores produce una invocación vacía que termina `SUCCEEDED`. El paso 1.5 levanta una excepción
  si hay `compilationErrors`.
- Un `try` o un `retry` alrededor de la ingesta haría seguir a Dataform después de un fallo. El paso 2
  (`test_ingesta_sin_try` y su prueba negativa) lo impide.
- La consulta de la invocación se queda en un bucle sin fin o gasta pasos. El intervalo es de 60 s (paso 1.7), y la
  ejecución de Workflows tiene su propio límite de duración. Con 60 s, una invocación de unos minutos usa pocas decenas
  de pasos por día, dentro del free tier de 5.000 pasos al mes de DEC-002.
- Si `compras-workflow` no tiene actAs sobre `compras-dataform`, `workflowInvocations.create` falla por permisos en la
  primera corrida real. El grant ya existe (`infra/modules/iam/main.tf:40`). El paso 4 lo expone en `workflow_actas`,
  y el `run "t11_permisos"` (paso 8) comprueba el rol, el miembro `workflow` y la cuenta `dataform`. Si alguien borra
  el grant, `test:infra` falla.
- Si `google_project_service_identity` no acepta `dataform.googleapis.com`, el `apply` falla antes de crear el
  repositorio. Plan B: en `infra/modules/iam`, se quita ese recurso y se agrega `data "google_project" "this"`
  (`project_id = var.project_id`). El miembro del agente pasa a ser
  `"serviceAccount:service-${data.google_project.this.number}@gcp-sa-dataform.iam.gserviceaccount.com"`, en
  `local.dataform_agent`, sin ningún número literal que marque `check:repo`. En `main.tftest.hcl`, el mock pasa a ser
  `mock_data "google_project"` con `defaults = { number = "0" }`. Las aserciones de `t11_repositorio_dataform` y
  `t11_permisos` esperan entonces `service-0@gcp-sa-dataform.iam.gserviceaccount.com`. Con el plan B, Google crea el
  agente al habilitar la API de Dataform (`module.apis`), y se mantiene el `depends_on` del paso 6. Si el grant falla
  porque el agente aún no existe, el usuario repite `scripts/it/tf-apply.sh`.
- Si la etiqueta `status` de `finished_execution_count` no toma el valor `FAILED` (la documentación no lista sus
  valores y la métrica está en Beta), la alerta de E4 nunca se dispara. Lo detecta la verificación de integración:
  antes de dar por cumplido E4, el usuario confirma el valor en el Explorador de métricas. Si es otro, se cambian el
  `filter` del paso 5 y la aserción de `t11_e4_alerta`.
- Al crear el agente de Dataform, el repositorio o los grants, el `apply` falla mientras no exista el agente o no se
  propague el permiso. El paso 4 crea el agente con `google_project_service_identity` y el paso 6 pone `depends_on`.
  Si el error es `actAs`, `scripts/it/tf-apply.sh` ya reintenta.
- CI no tiene permiso para crear los recursos nuevos o para conceder los roles de proyecto nuevos (la condición
  `hasOnly`). Lo cubre el paso 7, y el bootstrap reaplicado por el usuario es requisito del merge. `test:infra`
  comprueba los roles en el paso 8.
- El data source del canal no encuentra el canal o encuentra varios, y el plan falla. Depende del bootstrap aplicado
  (supuesto). El error aparece en `scripts/it/tf-plan.sh main` antes del `apply`.
- La cuenta del Workflow no puede esperar la operación del job. Lo cubre `roles/run.viewer` (paso 4). Si aun así
  falla, el `verify_integration` muestra `PERMISSION_DENIED` en el paso `ingesta_mercadopublico`, y en ese caso se
  cambia el rol del job por `roles/run.developer` sobre los jobs.
- Un mock aleatorio de un número de proyecto o una cuenta de 12 dígitos dispara `check:repo`. El paso 8 fija mocks con
  `service-0` y `notificationChannels/1`.
- El token de GitHub queda en la salida o en logs. El script no lo lee nunca. Terraform solo referencia el nombre de la
  versión, y `check:repo` sigue prohibiendo `google_secret_manager_secret_version` con datos.
- Cloud Scheduler reintenta y lanza dos corridas el mismo día, lo que cargaría la ingesta dos veces. El paso 5 fija
  `retry_count = 0`.
