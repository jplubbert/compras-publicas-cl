# Plan de T-04

## Objetivo

Cumplir REQ-002 con dos workflows de GitHub Actions y sus scripts de apoyo, sin llaves de cuenta de servicio (DEC-004)
y con verificación local sin nube (DEC-005):

- `.github/workflows/ci.yml` (evento `pull_request` hacia `main`): job `checks` que corre `npm run lint`, `npm test`,
  `npm run check:repo`, `npm run check:spec` y `dataform compile`; job `plan` con `needs: checks`, condición
  `github.event.pull_request.head.repo.full_name == github.repository` (E4), autenticación con
  `google-github-actions/auth` y `workload_identity_provider` (E1), `terraform plan` de `infra/main` y comentario del
  resumen en el PR.
- `.github/workflows/deploy.yml` (evento `push` a `main`): job `checks` igual al de `ci.yml` y job `apply` con
  `needs: checks`, `environment: production`, autenticación WIF y `terraform apply` de `infra/main` (E2). Las imágenes y
  la corrida de Dataform en `ci` no se agregan (las agrega T-08, REQ-006).
- Ningún workflow contiene `credentials_json` ni `service_account_key`; `id-token: write` aparece solo a nivel de job y
  solo en `plan` y `apply`, los dos jobs con el paso de `google-github-actions/auth` (E3, DEC-004).
- Si una comprobación falla, `checks` termina en error y `plan`/`apply` no corren (`needs`).
- Pruebas locales en `scripts/ci/tests/` (pytest + pyyaml) que corre `npm run test:workflows`, sin red ni credenciales
  (DEC-005). Lo que toca GCP o GitHub (`terraform plan/apply`, `gh`) va en los workflows y en
  `scripts/it/last-ci-run.sh`, el `verify_integration` de la tarea, que comprueba con `gh` que la última corrida de
  `ci.yml` en un PR pasó.

## Pasos

1. `scripts/ci/plan-comment.sh <archivo-de-salida-del-plan>`: script bash (`set -euo pipefail`, cabecera de comentario
   con uso y códigos de salida al estilo de `scripts/it/tf-plan.sh`) que escribe en stdout el cuerpo Markdown del
   comentario:
   - primera línea: el marcador `<!-- tf-plan:infra/main -->`;
   - título `### terraform plan · infra/main`;
   - la línea de resumen del plan: la primera línea que coincide con `^Plan: [0-9]+ to add, [0-9]+ to change, [0-9]+ to destroy\.`
     o, si no hay, la que contiene `No changes.`; también la línea `Changes to Outputs:` si aparece;
   - un bloque `<details><summary>Salida completa</summary>` con la salida dentro de un bloque de código, recortada a sus
     últimos 60000 caracteres (el límite de un comentario de GitHub es 65536) con la nota `(salida recortada)` cuando se
     recorta.
   - Sale 2 sin argumento o si el archivo no existe; sale 1 (mensaje `plan-comment: no plan summary found` en stderr) si
     no encuentra ni la línea `Plan:` ni `No changes.`. No usa red ni `scripts/env.sh`. `chmod +x`.
2. `scripts/it/tf-apply.sh`: script bash que copia la estructura de `scripts/it/tf-plan.sh` solo para la raíz `main`:
   valida `TF_VAR_project_id`, `TF_VAR_region` y `TF_VAR_github_repository` antes de `scripts/env.sh` (sale 1 nombrando
   la que falta), se re-ejecuta con `scripts/env.sh` si `COMPRAS_ENV` no está, corre
   `terraform -chdir=infra/main init -input=false -reconfigure -plugin-dir="$TF_PLUGIN_DIR" -backend-config="bucket=${TF_STATE_BUCKET:-${TF_VAR_project_id}-tfstate}"`
   y `terraform -chdir=infra/main apply -input=false -auto-approve -no-color`, y sale con el código de terraform. Sale 2
   si recibe algún argumento (uso: `scripts/it/tf-apply.sh`). `chmod +x`.
3. `scripts/it/last-ci-run.sh`: script bash (`set -euo pipefail`) que no pasa por `scripts/env.sh` (que fija
   `PATH=/usr/bin:/bin` y no trae `gh`):
   - si `command -v gh` falla: `last-ci-run: gh is required` en stderr y sale 2;
   - corre `gh run list --workflow ci.yml --event pull_request --limit 1 --json status,conclusion,url,headBranch --jq '.[0] // empty | [.status, .conclusion, .url, .headBranch] | @tsv'`
     (respeta `GH_REPO` si el usuario la define; `gh` la lee solo);
   - salida vacía: `last-ci-run: no ci.yml run on a pull request` y sale 1;
   - `status` distinto de `completed` o `conclusion` distinto de `success`: imprime `last-ci-run: <status>/<conclusion> <url>`
     y sale 1;
   - si pasó: imprime `last-ci-run: success <headBranch> <url>` y sale 0. Si `gh` falla, sale con su código.
   - `chmod +x`.
4. `.github/workflows/ci.yml`:
   - `name: ci`; `on: pull_request: branches: [main]` (sin `pull_request_target`);
   - `permissions: contents: read` a nivel de workflow (sin `id-token`);
   - `concurrency: group: ci-${{ github.event.pull_request.number }}`, `cancel-in-progress: true`;
   - `defaults: run: shell: bash` (GitHub corre entonces `bash --noprofile --norc -eo pipefail {0}`);
   - job `checks` (`runs-on: ubuntu-latest`, sin `permissions` propios): pasos `actions/checkout@v5` con
     `fetch-depth: 0` (`check:spec` recorre la historia desde `history_since` con `git rev-list`), `scripts/setup.sh`,
     y un paso por comprobación, en este orden: `npm run lint`, `npm test`, `npm run check:repo`,
     `npm run check:spec` y `scripts/env.sh bash -c 'cd dataform && node_modules/.bin/dataform compile'` (los cinco
     con `run:`; `npm run …` se llama como `scripts/env.sh npm run …` para usar el node de `.tools/`). Ningún paso
     lleva `continue-on-error`.
   - job `plan`: `needs: checks`; `if: github.event.pull_request.head.repo.full_name == github.repository`;
     `runs-on: ubuntu-latest`; `permissions: contents: read, id-token: write, pull-requests: write`;
     `env: TF_VAR_project_id: ${{ vars.GCP_PROJECT_ID }}`, `TF_VAR_region: ${{ vars.GCP_REGION }}`,
     `TF_VAR_github_repository: ${{ github.repository }}`; pasos:
     1. `actions/checkout@v5` (antes de la autenticación);
     2. `scripts/setup.sh`;
     3. `google-github-actions/auth@v2` con `workload_identity_provider: ${{ vars.WIF_PROVIDER }}` y
        `service_account: ${{ vars.CI_SERVICE_ACCOUNT }}` (las dos salidas `workload_identity_provider` y
        `ci_service_account` del bootstrap);
     4. `scripts/it/tf-plan.sh main | tee plan.txt`;
     5. `scripts/ci/plan-comment.sh plan.txt > comment.md` y
        `gh pr comment "${{ github.event.pull_request.number }}" --body-file comment.md` con
        `env: GH_TOKEN: ${{ github.token }}`.
5. `.github/workflows/deploy.yml`:
   - `name: deploy`; `on: push: branches: [main]`; `permissions: contents: read`;
     `concurrency: group: deploy-production`, `cancel-in-progress: false`; `defaults: run: shell: bash`;
   - job `checks`: los mismos pasos que el `checks` de `ci.yml` (paso 4);
   - job `apply`: `needs: checks`; `runs-on: ubuntu-latest`; `environment: production`;
     `permissions: contents: read, id-token: write`; el mismo `env` de `TF_VAR_*` que `plan`; pasos `actions/checkout@v5`,
     `scripts/setup.sh`, `google-github-actions/auth@v2` con las mismas entradas que en `plan`, y `scripts/it/tf-apply.sh`.
   - Un comentario en la cabecera indica que T-08 agrega aquí las imágenes y la corrida de Dataform en `ci`.
6. `scripts/ci/tests/test_workflows.py` (pytest + `yaml.safe_load`):
   - función `triggers(doc)` que devuelve `doc.get("on", doc.get(True))` (PyYAML 1.1 lee la clave `on` como `True`);
   - función `id_token_violations(doc)` que devuelve la lista de problemas: `id-token` en los `permissions` del workflow;
     un job con `id-token: write` sin paso `uses: google-github-actions/auth@…`; un job con ese paso sin
     `id-token: write`;
   - los literales prohibidos se arman por concatenación (`"credentials" + "_json"`, `"service_account" + "_key"`), como
     en `scripts/ci/check-repo.mjs`, para que el archivo de prueba no los contenga;
   - pruebas: E1 (`ci.yml` se dispara con `pull_request` a `main`; tiene `checks` y `plan`; `needs` de `plan` incluye
     `checks`; `plan` tiene un paso `google-github-actions/auth@…` cuyo `with` trae `workload_identity_provider`);
     `checks` corre las cinco comprobaciones (busca `npm run lint`, `npm test`, `npm run check:repo`,
     `npm run check:spec` y `dataform compile` en los `run`) y su checkout tiene `fetch-depth: 0`; `plan` corre
     `scripts/it/tf-plan.sh main`, `scripts/ci/plan-comment.sh` y `gh pr comment`, y tiene `pull-requests: write`;
     E2 (`deploy.yml` se dispara con `push` a `main`; `apply` tiene `environment: production` —como texto o como
     `{name: production}`—, `needs: checks`, paso de auth con `workload_identity_provider` y corre
     `scripts/it/tf-apply.sh`); los `run` de `checks` de `deploy.yml` son los mismos que los de `ci.yml`;
     E3 sobre cada `.github/workflows/*.yml` (el texto no contiene los dos literales prohibidos e
     `id_token_violations` devuelve lista vacía); E4 (el `if` de `plan` contiene exactamente
     `github.event.pull_request.head.repo.full_name == github.repository`); ningún workflow usa
     `pull_request_target`; ningún paso tiene `continue-on-error: true`;
   - pruebas negativas de las funciones: `id_token_violations` sobre un dict con `permissions: {id-token: write}` a
     nivel de workflow, y sobre un job con `id-token: write` sin paso de auth, devuelve un problema en cada caso.
7. `scripts/ci/tests/test_scripts.py` (pytest + `subprocess`, sin red):
   - `plan-comment.sh`: con una salida que trae `Plan: 3 to add, 0 to change, 0 to destroy.` el cuerpo empieza con el
     marcador y contiene esa línea; con `No changes. Your infrastructure matches the configuration.` contiene
     `No changes.`; sin ninguna de las dos sale 1; sin argumento sale 2; con una salida de 200000 caracteres el cuerpo
     mide menos de 65536 y contiene `(salida recortada)`;
   - `last-ci-run.sh` con un `gh` falso (script en un `tmp_path` puesto primero en `PATH`, `PATH=<tmp>:/usr/bin:/bin`)
     que anota sus argumentos en un archivo e imprime lo que trae la variable `FAKE_GH_OUT`: `completed\tsuccess\t<url>\tfeat`
     sale 0 e imprime la URL; `completed\tfailure\t…` sale 1; `in_progress\t\t…` sale 1; salida vacía sale 1 con
     `no ci.yml run`; los argumentos anotados contienen `run list`, `--workflow ci.yml` y `--event pull_request`; con
     un `PATH` sin `gh` (un directorio con enlaces solo a `bash` y a los comandos que usa el script) sale 2;
   - `tf-apply.sh`: sin `TF_VAR_project_id` (variables `TF_VAR_*` quitadas del entorno, como en
     `scripts/ci/tests/tf-plan.test.mjs`) sale 1 y nombra la variable; con un argumento sale 2.

## Supuestos

- `pyyaml==6.0.3` y `pytest==9.1.1` están en el grupo `dev` de `pyproject.toml` y `scripts/setup.sh` los instala con `uv sync --all-packages --locked`; `uv run --frozen` los encuentra sin red.
- PyYAML (YAML 1.1) carga la clave `on:` de un workflow como el booleano `True`.
- `pytest` con `scripts/ci/tests` como ruta solo recoge `test_*.py` y no intenta cargar los `*.test.mjs` del mismo directorio.
- `npm run test:ci` (glob `scripts/ci/tests/*.test.mjs`) no recoge los archivos `.py`.
- `scripts/ci/check-repo.mjs` revisa los archivos de `.github/` y de `scripts/ci/tests/` con la regla `credentials-json`; por eso los literales de las pruebas van concatenados.
- Los runners `ubuntu-latest` traen `bash`, `curl`, `git` y `gh`, y tienen red, así que `scripts/setup.sh` instala allí `.tools/` igual que en la laptop.
- `actions/checkout@v5` y `google-github-actions/auth@v2` son versiones mayores publicadas y vigentes (la de auth según docs/spikes/T-02-recursos.md §(f)).
- `google-github-actions/auth` exige `actions/checkout` antes y exporta `GOOGLE_APPLICATION_CREDENTIALS` con un archivo `external_account` que el proveedor `hashicorp/google` 8.8.0 acepta.
- `scripts/env.sh` solo reemplaza `PATH`; las variables `GOOGLE_APPLICATION_CREDENTIALS`, `TF_VAR_*`, `TF_STATE_BUCKET` y `GH_TOKEN` pasan al comando.
- GitHub no entrega el token OIDC a los PR que vienen de un fork aunque el job lo pida; la condición de E4 además salta el job `plan`.
- Un job con `needs` no corre si el job del que depende falla (sin `if: always()`).
- Con `fetch-depth: 0`, `history_since` y `status_log_since` de `spec/TASKS.json` existen en el clon y `npm run check:spec` pasa igual que en la laptop; en un PR, el commit de merge que crea `actions/checkout` lo excluye `rev-list --no-merges`.
- El usuario crea en GitHub el environment `production` (con su regla de aprobación) y las variables de repositorio `GCP_PROJECT_ID`, `GCP_REGION`, `WIF_PROVIDER` y `CI_SERVICE_ACCOUNT`; documentarlo es parte de T-15 (README).
- `gh run list` admite `--workflow`, `--event`, `--limit`, `--json` y `--jq`, y lee `GH_REPO`.
- `tests/acceptance/T-04*` no lo escribe esta tarea: no está en sus `touches` y el test-author está desactivado (LOG 2026-10-22).
- La cuenta de servicio de CI del bootstrap (T-03) tiene los roles para planear y aplicar `infra/main`, y el bucket de estado se llama `<project_id>-tfstate` (valor por defecto de `scripts/it/tf-plan.sh`).

## Riesgos

- `npm run check:spec` falla en CI por un clon superficial que no contiene `history_since`: lo evita `fetch-depth: 0` (paso 4) y lo comprueba `test_workflows.py` (paso 6).
- Un `id-token: write` a nivel de workflow da el token también a `checks`: los pasos 4 y 5 lo ponen solo en los jobs, y `id_token_violations` (paso 6) falla si aparece a nivel de workflow o en un job sin auth.
- Un PR de un fork intenta autenticarse: la condición `head.repo.full_name == github.repository` (paso 4) salta `plan`; la prueba E4 la comprueba (paso 6).
- Una tubería `tf-plan.sh | tee` oculta el fallo del plan: `defaults.run.shell: bash` activa `pipefail` (paso 4).
- El plan es más largo que el límite de un comentario: `plan-comment.sh` recorta a 60000 caracteres (paso 1) y la prueba de 200000 caracteres lo comprueba (paso 7).
- Un apply corre aunque falle una comprobación en `main`: `deploy.yml` repite `checks` y `apply` tiene `needs: checks` (paso 5); la prueba de E2 lo comprueba (paso 6).
- Dos applies a la vez sobre el mismo estado: `concurrency: deploy-production` sin cancelación (paso 5).
- Un archivo de prueba que contiene el literal prohibido hace fallar `check:repo`: los literales van concatenados (paso 6).
- Una versión mayor de una acción que no existe solo falla en GitHub, no localmente: queda en el supuesto de versiones y lo detecta `scripts/it/last-ci-run.sh` (paso 3) en la integración.
- `last-ci-run.sh` ejecutado con `scripts/env.sh` no encontraría `gh`: el script no lo usa (paso 3) y sale 2 con mensaje si falta.
- `checks` de `ci.yml` y de `deploy.yml` divergen con el tiempo: la prueba que compara sus `run` (paso 6) falla.
